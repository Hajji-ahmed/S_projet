# Relevés bancaires : import, pointage, soldes, PDF

> Texte déplacé tel quel depuis `CLAUDE.md` le 04/11/2026, dans l'ordre d'origine (en anglais, comme ce fichier).

**Pointage = the 74 business categories** (decision of 08/10/2026, replaces the rule of 02/10/2026): the list is `app/seeds/pointages.py` (labels exactly as given by the business, e.g. « A voir », « CHQ ISMAIL KABBAJ », « SIMTIS-TEFIL »; internal code = `normalization_service.pointage_code(libelle)`, `pointage_types.code` is now 60 characters). The old types Encaissement / Décaissement / Frais bancaires are inactive. At import, a line's pointage is, in this order: the known value of the file; else the **memory** (the most frequent active pointage of the company's operations with the same `label_key`, `Pointages.guess` in `import_service`); else `guess_pointage(libelle, categories)`: the category whose name appears as whole words in the label, the longest one winning (« AGIOS D'ECHELLE » before « AGIOS »), plus `POINTAGE_SYNONYMES` (COMMISSION(S) → COM, TENUE DE COMPTE → FRAIS, SALAIRE(S) → LA PAIE, INTERETS → INTERET, REMBOURSEMENT PRET); « A voir » is never automatic; else empty (shown « À choisir »). It never blocks a line and no longer depends on the direction. The pointage list is sorted by `label_key` (case and accents ignored). Migration 0017 created the categories, deactivated the old types and re-pointed the existing operations with the keyword rule (memory not used), one audit `repointage` per operation (dev database: 113 of 392 classified, 279 « À choisir »). Migration 0005 (02/10/2026) is history.

**Unsigned Montant column** (decision of 04/10/2026, e.g. BP « Format_Different »): when the file has a Montant column with no negative value and a Solde column, and the balance chain proves at least one debit, each line takes the direction proven by its balance (`import_service._direction_from_balances`, the first line uses the file's SOLDE INITIAL); an unproven line is an error « Sens introuvable… », never a silent credit. Migration 0008 (data only) applied this once to the statement already imported (9 operations moved to debit, line hashes recomputed, audit `correction_sens`).

**Since 12/10/2026**: a « SOLDE AU JJ/MM/AAAA » line is a balance even when it carries an amount (opening before the first operation, closing after; value = crédit − débit, so a balance in the Débit column is negative; `normalization_service.is_solde_au`, `_balance_line`), and a Solde column that copies each line's own amount (≥ 90 % of readable lines, `_solde_copie_du_montant`) is ignored (`solde_colonne_ignoree`, orange message) so SIMTIS computes the balances; the Validation step has a « Modifier les colonnes » button that reopens the column mapping. A dated or undated SOLDE INITIAL / ANCIEN SOLDE / SOLDE PRÉCÉDENT / REPORT line (or SOLDE FINAL / NOUVEAU SOLDE) whose debit and credit are empty, zero or a dash (banks often write 0 or « - ») is not an operation and is never shown in the preview: it gives the file's opening (closing) balance, used for the consistency check. Every imported statement is read and exported in the **standard format** (CDC §4), its 11 fields in this order: Société · Pointage · Banque · Date d'opération · Date de valeur · Libellé · Débit · Crédit · Solde · Lettrage / Escompte · Commentaire (`import_service.STANDARD_HEADERS`); `GET /api/statements/{id}/export` returns it as `.xlsx` (real Excel dates and numbers, zero debit/credit = empty cell), downloaded in the browser through `apiDownload` (`frontend/lib/api.ts`).

**One continuous statement per account** (business decision of 02/10/2026): every import is appended to the account's statement instead of appearing as a separate table. Storage is unchanged (one `bank_statements` row per file, for traceability and the closing-balance check); the page reads `GET /api/statements/accounts/{id}?from=&to=` (all the account's operations in **chronological order**: date, statement, then `bank_transactions.ordre`, the operation's rank in its statement in the order used to compute balances (migration 0021, decision of 08/10/2026): a file listed newest first is imported in file order, so the id never tells which operation closes a day; `import_repository.ORDRE_CHRONOLOGIQUE`, also used by the Banques table's « solde du jour », the opening-balance proposal and `recalculer-soldes`) and exports `GET /api/statements/accounts/{id}/export`; the per-file list is only a « Journal des imports ». The page shows only the last 50 operations of the statement and the last 10 imports of the journal, with an « Afficher plus » button (`showLast` / `showFirst` in `frontend/lib/statements.ts`); the summary and the export always cover the whole statement or period. The import wizard has two steps, **Fichier → Validation**: the analysis starts as soon as the account (chosen in `AccountPicker`, a custom listbox with bank logos) and the file are set, and goes straight to Validation; the column mapping only appears as a fallback when the columns are not recognised.

**Editable statements** (spec `docs/superpowers/specs/2026-10-02-releves-modifiables-design.md`): the Validation step is the statement as it will be saved, in the standard format, editable line by line (`EditablePreview`, pure rules in `frontend/lib/statementLines.ts`, money summed in `BigInt` cents), **no line can be added**; the confirmation sends the checked lines as a **JSON file part** `lignes` (a multipart text field is capped at 1 MiB by Starlette, about 3,700 lines), **every checkable line is checked by default** (decision of 08/10/2026: valid and error lines; **since 12/10/2026 a duplicate is only a line already in the database** (statements and Sage, `_mark_duplicates`): identical lines of the same file are two real operations, both « Valide », told apart by their rank in the line hash so a re-import recognises them one by one; `garder_doublons` is accepted without effect and there is no Doublons group button; `defaultChecked` in `frontend/lib/importLines.ts`, shared with Sage; an already-imported line is never checkable, an ignored line has no box; a checked error line blocks the confirmation until it is corrected or unchecked; « Tout cocher » / « Tout décocher »), the server re-checks each one with the same `_read_line` rules, keeps the original line hash (a corrected file-error line gets the hash of its final values), sets `bank_transactions.origine` (`Fichier` / `Corrigée`, migration 0006) and audits every correction. A line in error in the file is never accepted silently: untouched it is refused with its file reasons, a wrong-bank line is always refused, and a corrected one records `erreurs_du_fichier` in the audit.

**Changes of 08/10/2026**: (1) imports accept **`.xlsx` and `.xls`** (statements and Sage): `import_file.read_sheet` recognises the format from the file content (OLE2 signature → `xlrd`, else `openpyxl`) and returns the same values (dates as `datetime`, whole numbers as `int`, empty cell = None); tests build `.xls` files with `xlwt` (dev dependency, `tests/helpers.xls`); after a backend dependency change, rebuild with `docker compose build backend`. (2) The Validation step of both import wizards has clickable tiles (`FilterTile`, `lib/importLines.ts`): Lignes à importer · Lignes en erreur · Doublons · Lignes ignorées filter the table (second click shows all); the analysis now returns `lignes_ignorees` (`import_file.IgnoredLine`: Excel line number, reason, cells) shown read-only in `IgnoredLinesTable` (statement: SOLDE INITIAL / SOLDE FINAL / total / title line; Sage: title line, journal that is no account's Journal Sage, counterpart account); `nb_ignorees` always equals its length.

**Big files** (same day): imports accept up to **50 000 lines and 20 Mo** (`import_file.MAX_ROWS`, `MAX_FILE_BYTES`, mirrored in `frontend/lib/statements.ts`); the statement `lignes` JSON part may reach 60 Mo; already-imported hashes are looked up in batches of 5 000 (`HASH_BATCH`); the Validation previews (statements, Sage, ignored lines) show **100 lines per page** (`pageOf` in `lib/importLines.ts`, shared `components/ui/Pagination.tsx`), tiles filter and totals cover the whole file. Measured in the containers: 50 000-line statement analysed in 7 s and confirmed in 19 s, Sage export in 3 s and 10 s. (7)

**Header abbreviations** (same day, AWB « DT opération » / « DT valeur »): `import_file.field_for_header` also tries the header with `ABREVIATIONS` expanded as whole words (dt → date, val → valeur, lib → libelle, mnt / mt → montant, ope / oper → operation, deb → debit, cred → credit), for statements and Sage. **Statements without balances** (same day; **since 09/10/2026 also a Solde column filled only on some lines**: every empty Solde cell of a readable line is computed, a bank balance is kept, checked (`ecart_solde` = bank − expected, shown in orange, never blocking) and the computation restarts from it; when the first operation carries the bank balance, the opening is that balance minus its amount, locked, source « Solde de la banque sur la première opération du fichier »; computed balances are shown greyed in the preview): when no Solde cell of the file is filled, SIMTIS computes each balance (previous − débit + crédit, chronological order like `_balances`) from an opening balance (**decision of 09/10/2026**: taken in this order from the bank file's SOLDE INITIAL line (locked, with a warning when it differs from the previous statement's closing), the previous statement's closing balance (`import_repository.last_operation_before`, locked), then the Banques table; the user may enter it **only at the first import** of the account, i.e. no imported operation before the file (`solde_ouverture_modifiable`); a `solde_ouverture` sent for a locked opening gives 409, except the same value; earlier description follows): the file's SOLDE INITIAL line, else the latest known balance of the account before the first operation to import (last imported operation with a balance, or last daily balance, the most recent; `import_repository.last_known_balance`), else, **computed backwards** from the Banques table (decision of 08/10/2026): the daily balance **dated the file's last day** (since 09/10/2026 a later balance is no longer used: missing operations in between made the proposal wrong), minus the file's movements (already-imported lines excluded; `_opening_backwards`, `import_repository.first_balance_from`), else entered by the user (confirmation refused with 409 until given). The analysis returns `soldes_calcules`, `solde_ouverture_propose` / `_source` and each line's `solde_apercu` (preview only: `solde` stays empty so the line hash and the « corrigée » comparison are unchanged); the Validation step has a « Solde d'ouverture » field and recomputes live (`runningBalances` in `lib/statementLines.ts`); analyse and confirm take a `solde_ouverture` form field, and the server recomputes on the kept lines (never trusts the screen). Saved operations get `bank_transactions.solde_calcule = true` (migration 0018) and the closing balance becomes the daily balance. Computed balances are displayed like file balances (decision of 08/10/2026). An already imported statement is recomputed with `python -m app.cli recalculer-soldes --releve N --solde-ouverture X` (refused when the statement has file balances; audit `recalcul_soldes`); done on 08/10/2026 for the dev BP statement n° 12 from 5 000 000 (closing 5 274 070.32 on 30/09/2026).

**Bank statements in PDF** (statements only, a Sage PDF is refused): `import_file.read_sheet(..., pdf=True)` recognises `%PDF` and reads one virtual sheet « PDF » with **pdfplumber** (new dependency): ruled tables when the document has some (`lignes_pdf`), else columns deduced from the words' positions, common to all pages (`lignes_par_mots`: words → lines within 3 pt → cells split on gaps above half the word height → columns = overlapping cells of lines with 3+ cells; a cell goes to the first column it overlaps); page headers repeated on later pages are dropped; a PDF without text (scanned) or without a table gives 409; at most 500 pages. Everything after (header detection, mapping, Validation, balances, duplicates) is the Excel pipeline.

**Not calibrated on real bank PDFs** yet: check each bank's first PDF in the Validation step and use the column mapping if needed.

**Excel files with a wrong declared size** (05/11/2026): the BP export « Mouvements des comptes » (JasperReports, sheet « report4 ») is an `.xlsx` named `.xls`, whose sheet declares `<dimension ref="A1"/>` while it holds 26 662 rows; openpyxl's read-only mode trusted it and the import said « La feuille « report4 » est vide. ». `import_file._read_xlsx` now calls `reset_dimensions()` before reading, so every present row is read (statements and Sage alike; test `test_xlsx_with_a_wrong_dimension_is_read_entirely`).

**A lone dash is an empty date** (05/11/2026): in the same BP export, the pending operations « (*) » have « - » as value date, and every one of them was in « Erreur » (« Date de valeur : Date illisible : « - » »). `normalization_service.parse_date` now reads a lone dash (`-`, `–`, `—`, constant `TIRETS`, function `is_dash`, also used by `import_service._no_amount`) as an empty cell: the optional value date stays empty, a dash in the operation date gives « Date d'opération manquante. ». A dash in the reference is still kept as « - ».

**Period chosen before importing** (05/11/2026): the Validation step of a statement import has a « Période du … au … » block (`ImportWizard.periodPicker`): « Appliquer », « Après le dernier relevé (jj/mm/aaaa) » (from the day after the account's last imported operation, pending « (*) » excluded: `import_repository.last_operation_date`, API `derniere_operation_importee`) and « Toute la période ». It is applied by the server, not by the screen: `/import/analyse` and `/import/confirm` take `periode_debut` / `periode_fin` (AAAA-MM-JJ, unreadable → 422, start after end → 409), `import_service._lignes_de_la_periode` moves the operations dated outside to « Lignes ignorées » (« Hors de la période choisie (du … au …) »; an unreadable date stays in error), so the opening balance of a file without balances is the closing balance before the period (with the screen alone, the BP export « Mouvements des comptes », which starts in 2023, would have taken the balance of 18/07/2023); a file's SOLDE INITIAL (or FINAL) line is dropped when the period cuts lines before (or after). The confirmation re-analyses with the same period; the audit `import_releve` records `periode_choisie`. Statements only (not Sage). Reason: that BP export repeats operations already imported from the earlier statement, and they are not seen as duplicates (no Solde column, different references, labels corrected on 28/10 with their old hash).

**A movement without label is imported** (decision of 07/11/2026, no migration): a statement line whose label is empty is no longer an error (« Libellé manquant. » removed): it is imported with the label `import_service.LIBELLE_ABSENT` « (SANS LIBELLÉ) », capitals like every normalised label (`bank_transactions.libelle` stays NOT NULL), also when a line corrected in the editable preview is left empty (`lib/statementLines.ts` `checkDraft` no longer flags it). The text enters the line hash, so the same file imported again sees the line as a duplicate. The Sage import keeps « Libellé manquant. ». Prévisions (same day, no change): lines whose date has passed are never deleted, only hidden when the page date is later (`GET /api/position/previsions?date=` returns that day or later).

**Opening of a file without balances that repeats an imported day** (decision of 09/11/2026, no migration; replaces « the last imported operation before the file's first operation » of 09/10/2026 for files without a SOLDE INITIAL line or bank balance): the BMCE statement of 05/11/2026 repeated 21 lines of 04/11 already imported (duplicates) and added 3 new lines of 04/11. The opening was the closing of 03/11 and the computed balances left out the 21 duplicates (closing −16 705 799,00 instead of −24 838 581,39). New lines are saved after the day's existing ones (`ORDRE_CHRONOLOGIQUE`: date, statement, ordre), so the opening is now the last imported operation **up to and including** the day of the file's first new line (`import_repository.last_operation_before(..., jour_inclus=True)` in `import_service._proposed_opening`); the source still reads « Solde de clôture du relevé précédent, le JJ/MM/AAAA ». The warning that compares a file's own opening with the previous closing is unchanged. Still not handled: new lines dated before days already imported do not recompute those later days' balances.

**Production operation of 09/11/2026: CIH balances recomputed from 02/11** (backup `~/backups/simtis-2026-11-09-1113.sql.gz`, direct SQL in one transaction, audit `recalcul_soldes` on `bank_account` 4 with the old and new values and the motif). **Lines added to several imported days: following balances recomputed** (decision of 09/11/2026, no migration; completes the opening rule of the same day, which handled one day only, and makes the manual CIH operation above unnecessary next time). For a file without balances (`soldes_calcules`, not a pending-operations file), the preview interleaves the new lines with the operations already in the database after the first new day (per day: the existing ones first, then the new ones, in `ORDRE_CHRONOLOGIQUE`), so the displayed balances and the closing are right (`import_service._apercu_avec_la_suite`, pure `soldes_enchaines` with `Etape`: a balance written by the bank is kept and the computation restarts from it, an operation without a balance is skipped). On confirmation, `_recalculer_suite` recomputes every operation of the account after the new statement's first line, then the opening and closing of the statements it touched, their daily balances of source « Relevé » (the new statement's closing day is still written by `_closing_balance`), and writes one audit `recalcul_soldes` on `bank_account` (`avant`: number of operations changed, statements and daily balances; `apres`: the new values and `bank_statement_id`). Nothing is written when no existing balance changes. `import_repository.operations_depuis`. Tests: `test_lines_added_to_several_imported_days_recompute_the_following_balances`, `test_the_recompute_keeps_a_balance_written_by_the_bank`.

**Opening a line from the Banques table** (09/11/2026): `/releves?compte=&date=&ligne=` (`lireLienReleve` in `lib/statements.ts`, `useSearchParams` under a Suspense in `app/(app)/releves/page.tsx`) selects that account, opens its statement on the period from `date` to `date`, highlights the line (`DataTable` `isRowSelected`, teal-light) and scrolls it to the centre once; enough operations are shown for the line to be visible. **Amounts always with 2 decimals** (decision of 11/11/2026, display only, every screen: statements, Sage entries, reconciliation, position, banks, accounts, dashboard): `formatAmount` (`frontend/lib/format.ts`) now always shows 2 decimals (« 12 500,00 DH », « 0,00 DH »; before, only when there were cents).
