**P16 Administration, historique, rapports (done, 14/10/2026)**.

**P16.1** `/administration` (tabs shown per permission): `/api/admin/users` (`admin.users`: list, create with a server-generated one-time password returned once (`PasswordOut`), edit name / email / roles, `PATCH …/status` (deactivation closes the sessions), `POST …/password` (new one-time password, unlocks, closes sessions)), `/api/admin/roles` (`admin.roles`; read also with `admin.users`): custom roles « Personnalisé » (code `PERSO_<NAME>`, `admin_service.code_role`, `systeme = false`), permission matrix (`PUT` per role, the screen sends only the changed roles), delete only a custom role without users; `GET /api/admin/permissions` grouped by module. Guards in `services/admin_service.py`, all checked **before** any change: at least one active administrator (row lock on the ADMIN role), an admin cannot deactivate themself or drop their own ADMIN role, the ADMIN role keeps `admin.users` and `admin.roles` (locked boxes on screen), a system role keeps its code. Audits: `creation_utilisateur`, `modification_utilisateur`, `activation_utilisateur`, `desactivation_utilisateur`, `reinitialisation_mot_de_passe`, `creation_role`, `modification_permissions`, `suppression_role`. Permissions being reloaded on every request, a change applies at once (tested). Users cannot change their own password yet.

**Permissions per person** (decision of 23/10/2026, migration 0037): `user_permissions` (user, permission, `accordee` true = added / false = removed; PK per user and permission, ON DELETE CASCADE); effective permissions = the roles' + additions − removals (`auth_repository.get_permission_codes`, so `/api/auth/me` and every check follow at once); `GET` / `PUT /api/admin/users/{id}/permissions` (`admin.users`; `ajouts[]` / `retraits[]`, all or nothing; an addition already given by a role or a removal of a permission no role gives is ignored; an administrator keeps `admin.users` and `admin.roles`; unknown code or the same code in both lists gives 409; audit `modification_permissions_utilisateur` with the before / after lists; `admin_service.user_permissions` / `set_user_permissions`). Screen: « Permissions de cette personne » (shield icon) in Administration > Utilisateurs opens `UserPermissionsModal` (one box per permission grouped by module, « Par le rôle … » / « Ajoutée » / « Retirée » / locked for an admin, « Revenir aux permissions du rôle »; pure rule `changementsPersonne` in `lib/admin.ts`); the list shows a « +N / −N » badge (`UserOut.nb_ajouts` / `nb_retraits`). Restricting a person to some banks or companies is not built.

**P16.2** `/historique` (`audit.view`): `GET /api/audit` (filters `user_id`, `action`, `entite`, `entite_id`, `from` / `to` as Moroccan days, 50 per page, newest first by id), `/api/audit/filtres` (values present in the journal), `/api/audit/{id}` (before / after field by field, `differences`); `historique_service.ACTIONS` / `ENTITES` give the French labels, an unknown code stays readable; the list carries a `resume` only (an `import_releve` entry can weigh 77 KB), the detail is loaded when a row is unfolded. 36 000 dev entries: under 0.05 s per page.

**P16.3** Administration > Paramètres (new permission `admin.settings`, migration 0029, given to ADMIN): `GET` / `PUT /api/parametres/rapprochement` edits `reconciliation_rules` (criteria points 0–100 and active, DATE tolerance 0–30 days, FENETRE 1–60 days, thresholds; strong ≥ proposal; MONTANT must stay active; all or nothing; audit `modification_parametre` per changed rule; used by the next engine run), `GET` / `DELETE /api/parametres/mappings/{id}` (audit `suppression_mapping`, the next import detects the columns again; **since 03/11/2026, migration 0045**, a bank keeps one statement model per kind of file: `column_mappings.format_fichier` Excel (.xlsx and .xls) / PDF, read from the content by `import_file.format_fichier`, × `en_cours` (the separate pending-operation file), named « Relevé BP · Excel » / « Opérations en cours BMCE · PDF » (`import_service.nom_modele`), CHECK `format_fichier` and `format_si_banque` (format required for a bank model, absent for Sage), partial unique index `uq_column_mappings_banque_format`; `import_repository.latest_mapping(…, format_fichier, en_cours)` reads and `_save_mapping` updates only that model, so a PDF no longer overwrites the Excel model; the migration gave each existing model the format and kind of its bank's last confirmed statement (prod: all Excel), its downgrade keeps the newest per bank; Sage keeps one model per company). The fee-rise alert threshold stays 10 % in code.

**P16.4** `/rapports` (menu shown with `position.view` or `reconciliation.view`): `GET /api/rapports/position?company_id=&date=` (`position.view`, the Banques table of `position_banques_service.banques_table` in its imposed structure: LIGNE, one « facilité de caisse » row per day, TOTAL, DEPASSEMENT, Disponible Fc reel, a reused last balance in grey italics) and `GET /api/rapports/rapprochement?company_id=&from=&to=&bank_id=` (`reconciliation.view`, ≤ 5 years; **rebuilt on 30/10/2026**, the « Synthèse » and « À rapprocher » sheets are gone: the **validated** matches whose operation is dated in the period (`decisions_query` + `validated_matches`, like the lettrage; cancelled and rejected left out), one sheet per account of the company or of the chosen bank, bank operations on the left (Date · Libellé · Réf. · Débit · Crédit), Code · Type · Validé par · Validé le in the middle, Sage entries on the right (Date · Libellé · N° pièce · Débit · Crédit, in the account's currency through `debit_credit_sage`), one block of lines per match placed side by side, blocks alternating white / light grey with a thin line between codes, teal section and header rows, frozen headers, a total row per side; `rapports_service.etat_rapprochement`, `_feuille_rapprochements`; screen card with Du / Au (default 1 January → today) and `BankPicker`; dev data, BP 2026: 696 matches in 0.4 s); both audited `export_rapport`.
