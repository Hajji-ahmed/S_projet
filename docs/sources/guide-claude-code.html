1. Claude Code en une page

Claude Code est un assistant de programmation qui travaille directement dans le dépôt SIMTIS : il lit les fichiers, cherche dans le code, lance des commandes (Docker, tests, git) et modifie le code. Chaque action est affichée, et les actions sensibles attendent votre autorisation.

1tâche = 1 session
Planavant tout code
Preuveavant « c'est fait »
Push= production

Ce que Claude fait bien

  • Retrouver où une règle ou un écran est codé, et l'expliquer.
  • Diagnostiquer un bug à partir d'un message d'erreur ou d'une capture.
  • Écrire le code et ses tests en suivant les couches du projet (api/ → services/ → repositories/).
  • Lancer les vérifications de la CI et corriger ce qui échoue.
  • Tenir à jour la documentation : fiches docs/decisions/, CLAUDE.md, PDF.

Ce qui reste à vous

  • Décider des règles métier (les termes non résolus comme Lettrage / Escompte se demandent au métier, ils ne se devinent pas).
  • Valider le plan avant que le code soit écrit.
  • Relire le diff et tester à l'écran.
  • Décider du commit et du push, qui partent en production.
  • Toute opération sur les données de production.
La règle d'or. Claude propose, vous décidez. C'est la même logique que le moteur de rapprochement de SIMTIS : rien n'est validé sans un humain qui a regardé.

2. Démarrer une session

  1. Démarrez Docker Desktop. Les tests backend, la base et l'application tournent dans les conteneurs ; sans Docker, Claude ne peut rien vérifier.
  2. Ouvrez le dossier racine S_projet dans VS Code. C'est à la racine que se trouvent CLAUDE.md et .claude/, que Claude lit au démarrage. Ouvert sur un sous-dossier, il ne les voit pas.
  3. Ouvrez Claude Code : icône Claude dans la barre latérale ou en haut à droite de l'éditeur. Dans un terminal, tapez claude à la racine du dépôt.
  4. Écrivez en français. Claude répond en français et garde les termes métier (Rapprochement, Position disponible, LIGNE…).

Donner du contexte sans tout recopier

MoyenUsage

Ne collez jamais de secrets : contenu de .env, mots de passe, JWT_SECRET, jeton GitHub, clé SSH du serveur. Ce que vous écrivez dans la conversation sort de votre poste.

3. Ce que Claude sait déjà du projet

Claude ne garde aucun souvenir d'une conversation à l'autre, sauf ce qui est écrit dans des fichiers. Le projet est organisé pour qu'il retrouve l'essentiel à chaque session.

FichierRôle pour Claude
CLAUDE.md (racine)Lu automatiquement à chaque session : état du projet, règles qui traversent les modules, commandes, règles métier, environnement, production. Ce qui y est écrit est appliqué.
docs/decisions/<module>.mdUne fiche par module, avec chaque décision datée. Claude doit lire la fiche avant de travailler sur un module et y écrire toute nouvelle décision.
.claude/skills/simtis-planImpose un plan et votre accord avant toute modification de code, configuration, migration, test, Docker ou CI.
.claude/skills/simtis-designPalette teal, composants, pages et tableaux imposés (Banques, Devises, Prévisions). Chargé pour tout travail d'interface.
docs/specs/Documents d'autorité : cahier des charges, architectures, tableaux imposés, plan des phases.
Mémoire personnelleVos préférences retenues d'une session à l'autre (par exemple : une liste de propositions à cocher avant chaque plan). Dites « retiens que… » ; /memory pour la consulter.
.claude/settings.jsonCommandes déjà autorisées, qui ne redemandent pas la permission.
Ce que Claude ne sait pas. Ce qui a été dit dans une autre conversation, une décision prise en réunion et jamais écrite, l'état réel des données de production. Une décision métier qui doit durer va dans docs/decisions/ ; une règle qui touche plusieurs modules va dans CLAUDE.md. Demandez-le explicitement : « écris cette décision dans la fiche du module ».

Le plan (skill simtis-plan)

Pour toute tâche qui crée ou modifie un fichier de l'application, Claude présente d'abord un plan puis s'arrête. Avant votre accord, il peut seulement lire, chercher et lancer des commandes en lecture (tests, git diff). La documentation (*.md, skills) n'a pas besoin de plan.

Partie du planCe qu'il faut regarder
ObjectifEst-ce bien ce que vous voulez voir fonctionner, du point de vue de l'utilisateur ?
HypothèsesÀ lire en premier. Chaque hypothèse fausse devient un bug.
Fichiers et étapesLe périmètre est-il raisonnable ? Un fichier inattendu mérite une question.
Données et règlesTables, formules, permission, entrée d'audit, filtrage par société, devises.
Tests et vérificationUn test qui échouerait si la règle disparaissait ; un contrôle à l'écran avec un exemple chiffré.
Hors périmètre, questionsRépondez aux questions avant de donner votre accord.

Répondre au plan

  • « ok », « vas-y », « valide » : Claude implémente le plan tel quel.
  • « change l'étape 3 : … » : Claude refait le plan et attend à nouveau.
  • « seulement les étapes 1 à 3 » : il fait ces étapes et s'arrête.

Si Claude découvre en cours de route qu'il faut changer de fichier ou d'approche, il doit s'arrêter, expliquer l'écart et redemander votre accord.

Pour une idée encore floue, commencez par /superpowers:brainstorming : Claude propose une liste de choix à cocher, puis un plan construit sur vos choix. Pour un bug, /superpowers:systematic-debugging l'oblige à trouver la cause avant de proposer une correction.

5. Bien formuler une demande

Une bonne demande répond à cinq questions :

Où ?écran, société, banque, compte
Quoi ?ce qui se passe aujourd'hui
Attendu ?ce qui devrait se passer
Exempleune ligne, un montant, une date
Limitesce qui ne doit pas changer
À éviterMieux
« Le rapprochement ne marche pas. »« Sur /rapprochement, société Simtis, compte BMCE MAD : la ligne du 05/11 de −1 250,00 “FRAIS TENUE” n'est pas proposée avec l'écriture Sage de 1 250,00. Je m'attends à une proposition. Trouve la cause avant de corriger. »
« Ajoute une colonne. »« Dans la carte des frais à comptabiliser, ajoute la date de valeur après la date d'opération. Visuel seulement : pas de changement d'API ni de calcul. »
« Optimise l'import. »« L'import d'un relevé BP de 12 000 lignes prend 3 minutes. Mesure où passe le temps et propose avant de modifier. »
« Corrige les tests. »« pytest échoue sur tests/test_frais_service.py (sortie collée ci-dessous). Trouve la cause ; ne modifie pas le test pour le faire passer. »
« Fais le module Prévisions. »« Lis la fiche position-bancaire et la phase P14 du plan. Propose un plan pour la première étape seulement, avec tes questions sur les termes non résolus. »

Conseils

  • Un sujet par demande. Deux sujets mélangés donnent un plan flou et un diff difficile à relire.
  • Question ou modification ? Pour une simple question, dites-le : « réponds seulement, ne modifie rien ».
  • Bug : le diagnostic d'abord. « Cherche la cause, ne corrige pas encore » évite une correction posée sur la mauvaise cause.
  • Termes métier non résolus (Lettrage, Escompte, « Exp DH convertible », lecture du bloc Prévisions) : Claude doit poser la question. S'il propose une définition, refusez tant que le métier n'a pas confirmé.
  • Les tableaux imposés (Banques, Devises, Prévisions) ne se redessinent pas : colonnes, ordre et libellés viennent de SIMTIS_tableaux_complets.xlsx.

6. Garder le contrôle : permissions, interruption, retour arrière

Les modes de permission

Le mode se choisit sous la zone de saisie dans VS Code, ou avec Shift+Tab dans le terminal.

ModeComportementQuand l'utiliser
Demander (par défaut)Claude demande votre accord avant chaque modification de fichier et chaque commande non autorisée.Calculs, rapprochement, migrations, sécurité.
Accepter les modificationsLes modifications de fichiers passent sans question ; les commandes restent contrôlées.Un plan déjà validé, sur un sujet bien cadré.
Mode planLecture seule : Claude explore et propose un plan, sans rien modifier.Comprendre un module, préparer une phase.
AutoClaude enchaîne les actions avec ses propres garde-fous.Tâches répétitives à faible risque. À éviter près des données.

Autoriser une commande

Quand Claude demande à lancer une commande, lisez-la. « Oui, et ne plus demander » l'ajoute aux commandes autorisées du projet. Ne l'accordez jamais pour une commande destructive :

docker compose down -v # efface le volume de la base git push --force / git reset --hard rm -rf … / Remove-Item -Recurse -Force … psql … DELETE / UPDATE / DROP sur la vraie base python -m app.cli … --appliquer # opération de reprise sur les données

Interrompre et revenir en arrière

  • Échap arrête l'action en cours. Donnez ensuite la nouvelle consigne : Claude reprend avec.
  • /rewind (ou Échap deux fois dans le terminal) revient à un point antérieur de la conversation et peut restaurer les fichiers modifiés par Claude.
Le retour arrière ne défait pas les commandes. Une migration appliquée, un script lancé avec --appliquer ou un conteneur supprimé restent faits. Git et les sauvegardes restent le vrai filet de sécurité.

7. Vérifier le résultat avant de l'accepter

Selon CLAUDE.md, une tâche n'est terminée que si toutes les commandes de la CI passent. Claude doit montrer chaque commande lancée et son résultat réel. S'il écrit « c'est fait » sans sortie de test, demandez : « montre-moi la commande et sa sortie ».

# Backend docker compose run --rm backend ruff check . docker compose run --rm backend ruff format --check . docker compose run --rm backend pytest # Frontend (depuis frontend/) npm run lint && npm run format:check && npm run typecheck && npm test && npm run build

Relire le diff

Panneau Contrôle de code source de VS Code (Ctrl+Shift+G), ou demandez « montre-moi le diff ». Points à vérifier sur SIMTIS :

  • Les montants restent en Decimal côté Python et en chaînes exactes côté frontend, jamais en float.
  • Chaque requête filtre par société ; aucune somme entre devises.
  • Un nouvel endpoint a sa permission (require_permission) et écrit son entrée d'audit.
  • Une migration générée a été relue (triggers et fonctions manquent à l'autogénération) ; chaque nouvelle contrainte a son test dans test_constraints.py.
  • Les tests échoueraient si la règle était retirée ; aucun test n'a été affaibli pour passer.
  • La décision est écrite dans la fiche docs/decisions/ du module.

Tester à l'écran

docker compose up -d --wait, puis http://localhost:3000 avec un compte de démonstration. Refaites l'exemple chiffré de votre demande.

Faire relire par Claude

/code-reviewCherche les bugs dans les changements en cours.
/simplifyPropose des simplifications et du code réutilisable.
/security-reviewRevue de sécurité des changements de la branche, avant un push important.

8. Git, CI et production

Un push sur la branche hajji part en production. Le serveur (10.77.77.11) vérifie toutes les 5 minutes s'il y a un nouveau commit ; si toutes ses vérifications GitHub sont vertes, il fait une sauvegarde puis déploie. Avant de demander un push : CI locale verte, diff relu, test à l'écran.

Commit et push

  • Claude ne fait de commit et de push que si vous le demandez : « commit avec un message en français », puis « pousse » séparément.
  • Les messages suivent le style du dépôt : Module : ce qui change, par exemple « Frais : une ecriture par frais, toutes les lignes au libelle du releve ».
  • Un commit par sujet. Si le dossier contient des changements sans rapport, dites à Claude lesquels inclure.

Ce qui est interdit

Modifier du code sur le serveurLe serveur fait git reset --hard à chaque déploiement : toute modification locale y est perdue.
docker compose down -vSupprime le volume db_data, donc toutes les données.
git push --force, réécriture d'historiqueCasse le clone du serveur et l'historique partagé.
Contourner les hooks (--no-verify)Masque une erreur au lieu de la corriger.

Opérations sur les données de production

  1. Sauvegarde de la base, avec son nom de fichier noté.
  2. Simulation : le script lancé sans --appliquer, résultat relu.
  3. Application : --appliquer avec un motif.
  4. Trace : l'opération et sa sauvegarde sont écrites dans la fiche du module.

Claude prépare et explique ces étapes ; c'est vous qui lancez l'application sur le serveur.

9. Gérer le contexte et les sessions

Claude a une mémoire de travail limitée. Quand une conversation devient longue, elle est résumée automatiquement et des détails se perdent. Quelques habitudes évitent les problèmes :

HabitudeComment
Une session par tâche/clear entre deux sujets sans lien. La nouvelle session relit CLAUDE.md et repart propre.
Résumer volontairement/compact résume la conversation. Vous pouvez préciser quoi garder : « /compact garde les décisions et la liste des fichiers ».
Voir l'occupation/context montre la part de mémoire de travail utilisée.
Reprendre plus tard/resume rouvre une conversation passée ; dans le terminal, claude --continue reprend la dernière. VS Code garde aussi l'historique des conversations.
Écrire ce qui doit durerDécision métier → docs/decisions/. Règle transverse → CLAUDE.md. Préférence personnelle → « retiens que… » (mémoire).

Les agents en parallèle

Pour une recherche large (« vérifie toutes les requêtes qui ne filtrent pas par société »), Claude peut confier le travail à des sous-agents qui lisent beaucoup de fichiers et lui rendent seulement la conclusion. C'est plus rapide pour les gros audits, mais cela consomme davantage. Pour une question précise, ce n'est pas nécessaire.

12. Aide-mémoire

Avant

  • Docker Desktop démarré, VS Code ouvert sur S_projet.
  • Une tâche, une session (/clear sinon).
  • Demande avec : où, quoi, attendu, exemple, limites.

Pendant

  • Lire hypothèses et questions du plan avant « vas-y ».
  • Lire chaque commande avant de l'autoriser.
  • Échap dès que Claude part dans la mauvaise direction.

Après

  • Sortie réelle de chaque commande de la CI.
  • Diff relu, test à l'écran avec l'exemple chiffré.
  • Décision écrite dans docs/decisions/.
  • Commit, puis push en sachant qu'il part en production.

Phrases utiles

  • « Réponds seulement, ne modifie rien. »
  • « Cherche la cause avant de corriger. »
  • « Plan d'abord. »
  • « Seulement les étapes 1 à 3. »
  • « Visuel seulement : pas d'API ni de calcul. »
  • « Ne devine pas : pose la question. »
  • « Montre-moi la commande et sa sortie. »
  • « Ne modifie pas le test pour le faire passer. »
  • « Écris cette décision dans la fiche du module. »
  • « Retiens que… » (mémoire personnelle)
  • « Commit avec un message en français, ne pousse pas. »
À retenir. Claude propose, vous décidez ; rien n'est « fait » sans la sortie des tests ; un push sur hajji est une mise en production.
