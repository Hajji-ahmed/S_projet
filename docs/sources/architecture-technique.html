1. Vue d'ensemble

Une application web en trois conteneurs. Le navigateur ne parle qu'à l'API ; l'API applique la sécurité et toutes les règles métier ; PostgreSQL stocke les données normalisées et l'historique.

Règle d'architecture. SIMTIS est une couche d'intégration, de contrôle et de pilotage, pas un second Sage. Le frontend ne contient aucune règle métier ni calcul financier ; il ne parle jamais à PostgreSQL.

4. Frontend Next.js

4.1 Organisation

DossierContenu

4.2 Règles

  • Tout appel passe par apiFetch : jeton Bearer, un rafraîchissement sur 401 puis retour à /login, message « Requête refusée : données invalides. » pour un 422 sans message métier ; apiDownload pour les fichiers.
  • Le jeton d'accès reste en mémoire, jamais dans localStorage.
  • Argent : chaînes exactes ("500000.00") ; les sommes d'écran se font en centimes BigInt, jamais en float. formatAmount() pour tout montant affiché, formatCompact() (« 18 M ») pour les axes.
  • Société active : useCompany() ; chaque écran ne lit qu'une société.
  • Menu filtré par ROUTE_PERMISSIONS (lib/permissions.ts, copie vérifiée par un test de core/permissions.py). Masquer un menu ne protège rien : l'API vérifie.
  • Les tableaux Banques, Devises et Prévisions ont une structure imposée et n'utilisent pas DataTable.

  • Les erreurs métier sont levées par les services (NotFoundError → 404, ConflictError → 409, message en français) et converties par main.py en {"detail": message}.
  • Un nouveau routeur s'ajoute au protected_router de api/router.py (401 sans session) ; un nouveau modèle s'importe dans models/__init__.py (sinon Alembic ne le voit pas).

  • Date métier : business_today(), fuseau Africa/Casablanca.
  • Commandes : python -m app.seeds [--demo], python -m app.cli create-user, python -m app.cli recalculer-soldes.

8.3 Garanties en base

  • Un compte actif par (société, banque, devise, type) : index unique partiel ; un journal Sage par compte actif et par société : déclencheur.
  • Une seule correspondance active par opération et par écriture : index uniques partiels sur reconciliation_match_items.actif.
  • Code de rapprochement unique par société ; compteurs sans trou (INSERT … ON CONFLICT … RETURNING).
  • CHECK : décision tracée, montant devise de même signe, famille de frais posée exactement pour les écritures SIMTIS, TVA et taux cohérents, opération remplacée seulement si en cours…
  • audit_logs non modifiable (déclencheur) : ni mise à jour ni suppression.
Migrations. 35 migrations Alembic appliquées à chaque démarrage. Une migration générée se relit toujours (elle ignore déclencheurs et fonctions). alembic check ne compare pas les CHECK : chaque contrainte a son test dans tests/test_constraints.py. Les seeds créent sans jamais modifier ni supprimer.

›

›
En-tête & mappingSynonymes, abréviations, modèle mémorisé
›
Lecture des lignesNormalisation, erreurs, ignorées
›
ContrôlesSoldes, sens, doublons par lots de 5 000
›
ConfirmationUne transaction : lot, relevé, lignes, mapping, contrôle, solde, audit
  • Empreinte de ligne (hash) pour les doublons ; rang dans le fichier pour distinguer deux lignes identiques ; empreinte définitive gardée pour une opération en cours complétée.
  • Ordre chronologique : date, relevé, puis bank_transactions.ordre (rang dans le fichier), utilisé pour le solde du jour et les soldes calculés.
  • Soldes calculés : solde_calcule = true ; recalcul possible par app.cli recalculer-soldes.
  • Mesures : 50 000 lignes analysées en 7 s, confirmées en 19 s ; export Sage de même taille 3 s / 10 s.

10. Moteur de rapprochement

10.1 Étapes d'un lancement

  1. Verrou de la société en FOR UPDATE NOWAIT (un second lancement reçoit 409 immédiatement).
  2. Lecture des opérations libres (hors frais et opérations en cours) et des écritures libres de la période (≤ 5 ans).
  3. Paires comparables : même compte, sens opposé, types compatibles, fenêtre de dates (± 10 j, 180 j à montant et numéro égaux).
  4. Score par reconciliation_scoring, avec rejet rapide prouvé sous le seuil (points sans libellé, référence, bornes supérieures du ratio de libellé).
  5. Attribution du meilleur score au plus faible ; égalité → ambiguë ; second score gardé pour « Concurrente proche ».
  6. Groupes N → 1 (principal + commission + TVA 10 %) ; remplacement des seules propositions en attente du moteur ; audit.

11. Frais bancaires et export Sage

  • Propositions calculées, jamais stockées (GET /frais) ; la validation recalcule tout côté serveur, tout ou rien.
  • Écriture : accounting_entries avec origine = 'SIMTIS', famille_frais, N° pièce de frais_piece_counters (par société, banque, mois), plus un rapprochement validé d'origine « Frais ».
  • Lignes saisies par l'utilisateur dans frais_lignes ; journées écartées dans frais_jours_ecartes.
  • Export CSV : séparateur « ; », Windows-1252, virgule décimale, dates JJ/MM/AAAA, 15 colonnes de l'import paramétrable Sage ; marque exportee_le. Refusé pour un compte EUR / USD (pas de taux).
  • Seuil SEUIL_MANUEL = 200 DH pour les familles COM et FRAIS ; justificatif Excel pour la banque.

12. Sécurité

ConnexionMot de passe argon2
›
SessionCookie HttpOnly limité à /api/auth
›
Jeton d'accèsJWT en mémoire, porte l'id de session
›
PermissionsRechargées de la base à chaque requête
›
API401 / 403 avant tout traitement
  • Les permissions ne sont jamais dans le JWT : un changement de rôle s'applique tout de suite ; déconnexion, changement de mot de passe et désactivation coupent l'accès immédiatement.
  • Tolérance d'horloge de 60 s au décodage (l'horloge de la VM Docker recule parfois).
  • tests/test_permissions.py échoue si une route répond sans jeton hors liste publique.
  • Codes de référence (banques, sociétés, rôles) immuables ; schémas d'entrée stricts (champ inconnu → 422).
  • CORS limité aux origines configurées.

13. Audit et traçabilité

  • audit_service.log(db, user_id, action, entite, entite_id, avant, apres, ip) dans la même transaction que la modification, puis un seul commit.
  • Masquage automatique des mots de passe et jetons ; Decimal stockés en texte exact.
  • Plus de 60 actions tracées : imports, corrections, suppressions d'opérations en cours, propositions, validations, rejets, annulations, rapprochements manuels et élargis, comptabilisations, exports, administration, paramètres.
  • Lecture par /api/audit (50 par page, < 0,05 s sur 36 000 entrées) ; le détail n'est chargé qu'à l'ouverture d'une ligne.

15. Exploitation et évolutions

15.1 Mise en production (à faire)

  • Images de production : next build + next start, Uvicorn sans rechargement, variables d'environnement de production (APP_ENV=production refuse les données de démo).

  • Sauvegarde quotidienne de PostgreSQL (pg_dump) et test de restauration.
